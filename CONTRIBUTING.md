# Contributing

Thank you for helping. The Dream Engineering Project is research software: the
bar for a change is "does it make the evidence better, the study safer, or the
code easier to trust". Please read [SAFETY.md](SAFETY.md) and the
[Code of Conduct](CODE_OF_CONDUCT.md) first.

## Setup

You need Node.js (the project is developed and tested on Node 24) and, for the
browser QA only, a local installation of Google Chrome.

```sh
npm install
npm test          # 71 unit tests, no browser needed, under a second
npm run qa        # end-to-end browser QA in headless Chrome, about 10 minutes
npm run serve     # http://localhost:8787
```

There is no build step. The app is vanilla ES modules, so edit a file and
reload.

### What the checks cover

- `npm test` runs the pure logic in `js/core/` (randomisation, scoring,
  statistics, the safety rules, schema migration, CSV round trips) with
  Node's built-in test runner.
- `npm run qa` (`qa/browser-qa.mjs` and `qa/phase2-qa.mjs`) drives the real UI
  in a throwaway headless Chrome profile with a fake microphone. It runs at
  60x speed, mutes all audio (including speech synthesis, which is stubbed)
  and writes screenshots, fixtures and exports to `qa/out/`, which is
  git-ignored.

Please run both before opening a pull request that touches `js/`, `css/`,
`index.html` or `sw.js`. If you add behaviour, add a unit test for the logic
and, if it changes what a person sees or does, a browser check.

A passing run is evidence that the software does what we wrote down. It is not
evidence that dream engineering works. Keep those two things separate in
anything you write.

## Data is never committed

This project handles private material: dream reports, voice recordings,
check-ins. Never commit, attach to an issue, or paste into a pull request:

- backups or exports from the app (`dream-engine-backup-*.json`, trial or
  session CSVs, rater packets);
- recordings or screenshots of real reports;
- anything that identifies you or anyone else.

Test fixtures and screenshots in this repository are synthetic, generated by
`qa/browser-qa.mjs`. If you share a result, share summary statistics, or a
synthetic reproduction. The `.gitignore` covers the usual export names, but it
is not a substitute for checking `git status` before you commit.

## Proposing a protocol change

The protocol in [docs/PROTOCOL.md](docs/PROTOCOL.md) is written like a
pre-registration, and a study's protocol is locked when it is created. Changes
therefore go through a proposal, not a drive-by edit.

1. Open an issue with the **Research proposal** template.
2. State the change, the question it addresses, and the evidence for it: a
   citation with authors, year, journal and DOI, or data from a replication.
   Say how strong the evidence is and whether it is established or a
   hypothesis.
3. Say what happens to existing studies. New behaviour must be versioned (see
   `studyProtocol` in `js/core/study.js` and `docs/SPEC-v0.4.md`), and studies
   created earlier must keep behaving exactly as they did.
4. Say what would change your mind: what result would show the change was a
   mistake.
5. Safety first: changes that add wake-ups, lengthen sessions, widen the time
   window, add stimulation channels or remove a pause rule need a stronger
   case than any other change.

Changes that make the study less honest (unblinding, post-hoc outcomes,
dropping unfavourable sessions) will not be accepted, however convenient.

## Reporting a replication

If you ran the protocol, a replication report is the most valuable
contribution there is, including a null result. Use the **Replication report**
issue template, and report what the protocol says you should: the pre-set
number of sessions, all of them, and the blind scores. See
[docs/PROTOCOL.md](docs/PROTOCOL.md).

## Pull requests

- Keep each pull request to one change, with a clear description of why.
- Match the existing style: no framework, no build tooling, no runtime
  dependencies. `playwright-core` is a dev dependency used only by the QA.
- Do not add network calls, analytics, fonts or scripts loaded from elsewhere.
  The page's content security policy blocks outbound requests by design, and
  that guarantee is part of the project's privacy promise.
- Update `docs/` and `CHANGELOG.md` when behaviour changes.
- Use the pull request template and tick the checklist honestly.
